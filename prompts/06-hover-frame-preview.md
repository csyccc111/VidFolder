规划与提示词：OpenAI Codex（GPT-5），2026-08-13。

## 背景

你是一名资深 Electron + React + TypeScript 桌面应用工程师。请在现有 Vid Folder Browser 项目上进行 v0.6 增量开发。

本版本只增加“网格封面悬停多帧预览”。用户在封面区域水平移动鼠标时，可查看视频不同时间位置的代表帧，从而不打开播放器就判断视频内容。

重要规则：

- 开始前阅读 `PROJECT_MEMORY.md`、`PROMPT_VERSIONING.md`、v0.4/v0.5 Prompt、README 和当前实现。
- v0.5 应已完成并通过回归；不要在本版本再次重构整体 UI。
- 沿用 v0.4 的错误模型、缓存安全规则和 v0.5 的 shadcn/ui 组件体系。
- 多帧预览必须按需生成，不能在普通扫描阶段为全部视频预生成。
- 本功能不能阻塞扫描、普通封面生成、窗口交互或应用退出。
- 不实现视频播放、音频播放或自定义封面。
- 中文内容和源码统一使用 UTF-8。

把项目视为已经具备 v0.1-v0.5 的全部能力，包括：

- 文件夹扫描、视频封面和元信息缓存。
- 网格/列表、搜索、排序、筛选、详情和右键操作。
- ffmpeg/ffprobe 检测、分阶段错误模型、缓存校验与自愈。

这些都不是本版本的重新实现目标。

## 本版本目标

- 让用户通过封面区域快速查看视频多个时间位置。
- 控制 ffmpeg 任务数量、CPU 使用、磁盘缓存和 IPC 生命周期。
- 在快速移动鼠标、切换筛选、切换文件夹或退出应用时保持状态正确。
- 缺少依赖、短视频、损坏视频和任务失败时优雅回退到静态封面。

## 交互定义

- 仅网格视图的视频封面启用多帧预览；列表视图不启用。
- 鼠标进入封面后延迟约 400ms 激活，快速掠过不启动生成任务。
- 激活后，根据鼠标在封面内的水平位置映射到预览帧索引：左侧对应较早时间，右侧对应较晚时间。
- 默认采用 8 个代表帧，时间点分布在视频有效时长的约 5% 到 95%，避免首尾纯黑帧。实际算法应处理极短视频和未知时长。
- 鼠标离开时立即恢复主封面，取消尚未开始的预览请求。
- 已生成帧切换应即时，不显示白屏或破图；尚未就绪时继续显示主封面和低干扰加载状态。
- 封面角落显示当前帧对应的视频时间，格式复用现有时长格式化规则。
- 同一时刻只允许一个视频处于可见预览状态。
- 触屏或无 hover 能力的环境不启用该交互。
- 提供一个紧凑的“悬停预览”开关并持久化，默认开启。缺少 ffmpeg 时开关禁用并用 Tooltip 说明原因。

## 本版本只做

### 1. 预览帧数据和缓存协议

- 预览缓存必须与普通主封面分离，建议目录：`preview-cache/<source-key>/<schema-version>/` 或等价安全结构。
- 预览缓存 key 至少包含现有源文件 key（路径、大小、mtime）和预览算法版本。
- 预览算法版本应覆盖帧数、时间点策略、尺寸或编码参数变化，避免配置变化后误用旧帧。
- 每帧文件名使用受控索引或 hash，不把任意渲染进程路径直接拼入文件系统路径。
- 通过受限协议 URL 或现有安全资源协议向前端提供图片；严格校验文件名和缓存目录边界，禁止目录穿越。
- 缓存记录至少包含：源 key、帧索引、时间点、图片路径/URL、状态和必要错误信息。
- 源视频变化后旧预览不得命中；失效预览按安全策略清理。
- 缓存文件缺失、零字节或 JPEG 头无效时自动降级并重新生成。

### 2. 按需抽帧策略

- 普通文件扫描和主封面生成不得自动触发多帧预览。
- 只有 hover 延迟完成且视频仍为当前目标时，才发起预览请求。
- 已知视频时长时按比例计算 8 个时间点；未知时长时可先尝试复用/补充元信息，失败则回退静态封面，不得对同一失败视频无限重试。
- 极短视频应减少重复时间点或减少帧数，保证时间点有效且递增。
- 可以一次 ffmpeg 调用生成多帧，也可以受控地逐帧生成；应根据取消能力、失败隔离和实测性能选择，并记录理由。
- 生成尺寸与当前网格最大显示需求匹配，不保存原视频分辨率截图。
- ffmpeg 参数必须使用参数数组传递，继续支持中文、空格和特殊字符路径。

### 3. 队列、优先级和取消

- 预览任务使用独立的有界队列，并发默认 1。
- 用户当前悬停请求优先于尚未开始的后台主封面任务，但不得粗暴终止已经接近完成的普通任务；具体调度应保持简单、可解释。
- 每个预览请求具有唯一 requestId，并关联视频 id、源 key 和当前扫描 token/目录上下文。
- 鼠标离开、切换视频、切换视图、改变筛选导致卡片消失、切换根文件夹或取消扫描时，应取消尚未开始的请求并忽略陈旧响应。
- 若实现运行中 ffmpeg 取消，应只终止该请求拥有的子进程；不得终止其他扫描或封面任务。
- 主进程不信任渲染进程传入的任意文件路径。请求必须对应当前已扫描的合法视频项，扩展名和路径需验证。
- 应用关闭时停止接收新任务，并清理预览子进程和待执行队列，避免残留进程。

### 4. IPC 设计

- 使用明确的请求/结果类型，不通过现有 `VideoItem` 的主封面字段复用预览状态。
- 建议语义：
  - 请求或获取预览帧。
  - 取消指定 requestId。
  - 接收预览进度/帧就绪/完成/失败事件。
  - 获取预览缓存统计。
  - 清理预览缓存。
- 所有事件携带 requestId 和 videoId，前端只接受仍与当前 hover 会话匹配的结果。
- preload 只暴露完成该功能所需的最小 API，不暴露 Node、文件系统或任意命令执行能力。
- 事件监听器必须在组件卸载时解除，避免重复订阅和内存泄漏。

### 5. 前端预览状态

- 将预览会话状态与视频的永久扫描数据分离。不要向主 `items` 数组持续写入每次鼠标位置变化。
- 对鼠标移动做轻量索引计算或必要节流，不能每个 pointermove 都触发 IPC 或昂贵 React 更新。
- 预加载相邻帧，但不一次把所有缓存图片长期保留为解码后的 DOM 图片。
- 快速从视频 A 移到 B 时，A 的迟到结果不得覆盖 B。
- 预览失败时本次 hover 回退主封面，并显示简短 Tooltip 或非阻塞状态；不弹模态框。
- 错误沿用 v0.4 分类，用户文案与技术详情分离。
- 主封面、时长角标、选中状态、右键菜单和双击打开行为不能被预览层遮挡或误触发。
- 多帧图片切换不能改变卡片尺寸或推动周围布局。

### 6. 缓存容量治理

- 预览缓存必须有独立容量上限，建议默认 512 MiB；如果现有真实数据表明该值不合适，可以调整并记录理由。
- 使用近似 LRU 策略：按最近访问时间优先淘汰旧视频的整组预览帧，避免留下半组难以解释的状态。
- 容量检查和淘汰不能阻塞 UI，也不能在每次 pointermove 时执行。
- 提供用户可触发的“清理预览缓存”操作，并显示清理前后的项目数或占用空间。
- 清理仅允许操作预览缓存目录。规范化并验证目标路径，不跟随范围外路径，不触碰主封面缓存或用户视频。
- 清理正在显示或正在生成的预览时应先协调任务状态，避免文件竞争和破图。

### 7. 性能和验证

- 在实现前记录静态封面基线，实现后比较：应用启动、普通扫描、网格滚动和内存不能因未触发 hover 而明显退化。
- 至少测试连续悬停 50 个不同视频、在 10 个视频间快速往返、长时间停留、扫描过程中预览、切换文件夹时预览和缓存达到上限后的淘汰。
- 记录首次生成延迟、缓存命中切换延迟、单组平均磁盘占用、连续悬停 CPU/内存趋势和失败率。
- 验证 5000+ 视频目录不会在加载时自动创建成千上万组预览任务。
- 若 v0.4 性能基准尚未完成，不能声称 v0.6 通过大目录性能验收；应明确记录测试缺口。

## 建议类型

以下只表达协议语义，可按现有代码调整：

```ts
type PreviewFrame = {
  index: number;
  timestamp: number;
  imageUrl: string;
};

type PreviewRequest = {
  requestId: string;
  videoId: string;
  filePath: string;
  sourceKey: string;
};

type PreviewResult = {
  requestId: string;
  videoId: string;
  state: "loading" | "ready" | "failed" | "cancelled";
  frames: PreviewFrame[];
  error?: ItemError;
};

type PreviewCacheStats = {
  bytes: number;
  videoCount: number;
  frameCount: number;
};
```

不要让渲染进程自行提供可信的 `sourceKey`；主进程应根据已知视频状态计算或核验。

## 本版本不做

- 不做多候选封面选择、保存某帧为主封面或手动输入截帧时间。
- 不做内置播放器、视频流播放、音频、时间轴拖动或逐帧编辑。
- 不在列表视图启用多帧预览。
- 不在扫描时批量预生成全部视频的预览。
- 不加入标签、视频收藏、文件操作、实时目录监控或导出功能。
- 不内置或自动下载 ffmpeg。
- 不重构 v0.5 的整体 UI、文件夹树或快速访问。
- 不把预览缓存与普通封面缓存混为同一生命周期。

## 验收标准

- 未悬停时不创建预览任务，普通扫描性能和主封面行为无明显退化。
- 网格卡片停留约 400ms 后进入预览，水平移动能稳定映射到不同时间帧。
- 鼠标离开立即恢复主封面；快速移动不会出现其他视频的迟到帧。
- 默认 8 帧策略对正常、短、未知时长和损坏视频都有明确行为。
- 同时只有一个可见预览会话，预览 ffmpeg 并发默认不超过 1。
- 缺少 ffmpeg 时功能禁用并解释原因，应用其他能力正常。
- 预览失败不破坏主封面、元信息或已有缓存。
- 源视频变化后旧预览不命中，损坏预览可自愈。
- 预览缓存容量受控，超过上限后按组淘汰；手动清理不触碰主封面和用户视频。
- 切换视图、筛选、文件夹、取消扫描和退出应用时无陈旧 UI、未捕获异常或残留子进程。
- 连续悬停和快速切换压力测试有记录，CPU、内存和磁盘增长有边界。
- `npm run typecheck`、`npm run build` 和相关测试通过。
