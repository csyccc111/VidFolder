# v0.6 悬停多帧预览验证记录

实施：DeepSeek-V4 Flash，2026-08-13。

## 实现方式与理由

- **抽帧**：一次 ffmpeg 调用生成全部帧（`select=between(t,...)` 时间窗口 + `scale=480:-1` + `-vsync vfr`）。理由：进程启动成本占主导，逐帧调用延迟累计明显；生成后按帧文件逐一校验 JPEG 头，缺帧/坏帧整组回退，失败隔离由"帧文件校验 + 源 key 缓存"兜底。
- **时间点**：时长 1 秒以上取 8 帧，均匀分布在 5%-95%；不足 1 秒自动减帧（最少 2 帧），毫秒精度去重保证递增。未知时长先复用元信息缓存，仍未知则 probe 一次，失败回退静态封面。
- **缓存**：`preview-cache/<sourceKey>/`（与主封面 `cache/` 分离），`sourceKey = sha1(路径|大小|mtime)`，meta.json 记录版本号；版本变化或帧文件校验失败自动重建。
- **队列**：独立有界队列（并发 1，排队上限 8）；同 sourceKey 请求合并等待者；requestId 取消只移除等待者，运行中的 ffmpeg 不粗暴终止（生成幂等 + 帧校验自愈）；应用退出时 kill 子进程。
- **容量**：默认上限 512 MiB，生成完成后按近似 LRU 整组淘汰（跳过当前组），淘汰检查不在每次指针移动时执行。
- **安全**：请求路径必须命中主进程扫描缓存（metadataCache）且扩展名受支持；预览帧 URL 为受控结构（`preview://cache/<40hex>/v1_<n>.jpg`），协议处理器严格校验并限制在预览缓存目录内。

## 手动验证项（尚未自动覆盖）

- 512 MiB 容量上限的整组淘汰行为（需数千组数据，自动化成本高；LRU 选择逻辑已有单测 `pickLruEviction`）。
- 扫描过程中 hover 预览、切换文件夹时预览的竞态组合。
- 触屏设备无 hover 能力时的行为（UI 层仅网格启用，未做触摸特殊处理）。
- 超大目录（5000+ 视频）首次加载不产生预览任务：设计上预览只在 hover 延迟完成后发起，扫描路径无预览调用，代码审查确认无批量预生成；完整基准依赖 v0.4 性能基准（未执行）。

## 已知边界

- 运行中的生成任务不因鼠标离开而终止 ffmpeg（避免半组文件与 kill 竞态）；其完成后帧组可用，下次 hover 直接命中。
- 单帧缺失/损坏导致整组重建，重建前该组不可用（回退静态封面）。
